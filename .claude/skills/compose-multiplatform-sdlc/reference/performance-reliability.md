# Performance, reliability & observability reference

Measure on the reference **low-end** device of each platform (e.g. the oldest supported iPhone with the least RAM), on a throttled network, with **release builds**. The budgets come from the NFRs.

**Never judge iOS performance on a debug build.** A debug Kotlin/Native framework is unoptimised and can be several times slower than release.

## Performance
### Startup
- **Little work before the first frame.**
  - Android: a lean `Application.onCreate`; SDKs initialised lazily or with App Startup.
  - iOS: a lean `App.init`; native SDK set-up only where the SDK requires it at launch.
  - Starting Koin is cheap; resolving heavy singletons (the database, the HTTP client) happens on first use, off the main thread.
- **Android:** ship a Baseline Profile and a Startup Profile, generated by a Macrobenchmark module. They cover the shared code compiled into the app too. Regenerate them every release.
- **iOS:** measure launch with Xcode Instruments (App Launch) and the launch metrics in Xcode Organizer. The first Compose frame costs more than a plain UIKit view; keep the first screen light.
- **Local data first.** Show content from the local database, then refresh in the background.
- **Splash.** The SplashScreen API on Android and a static launch screen on iOS, with no artificial delay.

### Rendering (Compose)
- **Read state as late as possible.** Pass lambdas (`{ offset }`) for fast-changing values, and use `derivedStateOf` for values derived from them.
- **Lists.** Use stable, immutable UI models. Lazy lists get a `key` (`items(notes, key = Note::id)`), plus a `contentType` when items are mixed.
- **No allocation or sorting during composition.** Do that work in the ViewModel.
- **When a screen janks,** check the Compose compiler reports and the recomposition counts in Layout Inspector (Android), then confirm on iOS with Instruments (hitches, Time Profiler). iOS devices with ProMotion run at 120 Hz, so the frame budget is half of Android's usual 60 Hz.
- **Interop views** (`UIKitView`, `AndroidView`) are measured separately; each one adds cost.

### Main thread, memory and network
- **Main thread.** StrictMode in Android debug builds catches disk and network access. On iOS, the Main Thread Checker and Instruments' hang detection do the same job.
- **Leaks.** LeakCanary in Android debug builds; Xcode's memory graph and the Leaks instrument on iOS. Never hold an Activity, Context or `UIViewController` in a singleton or ViewModel.
- **Kotlin/Native memory.** The garbage collector handles Kotlin objects. Loops that create many Objective-C objects (e.g. `NSData`, `NSString`) run inside `autoreleasepool { }` so their memory is released per iteration.
- **Images:** Coil loads them at the displayed size, with bounded memory and disk caches.
- **Lists and network:**
  - Paging 3 for long lists.
  - HTTP caching that honours `Cache-Control` (Ktor's `HttpCache` plugin).
  - Work that belongs to a screen runs in `viewModelScope`, so it's cancelled with the screen.

### Size and battery
- **App size.**
  - Android: R8 full mode, resource shrinking, AAB delivery; review the APK Analyzer before each release.
  - iOS: Compose Multiplatform and the Kotlin runtime add several MB to the app. Check the App Store Connect size report per device before each release; keep `export`s and public API small; ship only the resource densities and fonts the app needs.
  - Vector images, WebP for bitmaps.
- **Background work** runs only through the `SyncScheduler`, with constraints (network, charging, battery not low) where the platform supports them.
  - Never poll; use push (FCM, APNs).
- **Location.** Ask for coarse or approximate location unless precise is required, and stop updates when nothing on screen needs them.

## Reliability
- **Offline-first,** where the requirements need it. Room is the single source of truth: the UI observes it, and the network refreshes it. The same code runs on both platforms.
- **Offline writes.**
  - Save locally and mark the change as pending; the UI shows it as pending.
  - Sync it through the `SyncScheduler`:
    - Android: a unique WorkManager job with network constraints and backoff.
    - iOS: on every return to the foreground, plus a `BGAppRefreshTask` that iOS runs when it chooses; an in-flight write is finished with a background-task assertion. Nothing guarantees the sync runs while the app is in the background.
  - Send an **idempotency key**, so a retry can't create a duplicate.
- **Retries.**
  - Exponential backoff with jitter (Ktor's `HttpRequestRetry` plugin).
  - Honour HTTP 429/503 and `Retry-After`.
  - Never blindly retry a call that isn't idempotent.
- **Conflicts** follow the policy from the architecture document, e.g. last write wins on server timestamps, or the user resolves them.
- **Tolerant parsing.**
  - `Json { ignoreUnknownKeys = true }`.
  - Defaults for optional fields.
  - An `UNKNOWN` value for enums.
- **Room migrations.**
  - Schemas exported and committed.
  - A migration test for every version (Room's `MigrationTestHelper`, run on the JVM or an Android device; the schema is the same on iOS).
  - An upgrade test on **both** platforms, from the previous store version.
  - Never a destructive migration in production.
- **Termination and configuration changes.**
  - UI state lives in ViewModels, which survive Android configuration changes.
  - Android process death: inputs restored from `SavedStateHandle` or `rememberSaveable`; test with "Don't keep activities".
  - iOS termination: no state is restored, so drafts and unfinished forms are written to local storage. Test by terminating the app in the background.
  - Navigation arguments live in routes.
- **Uncaught exceptions on iOS** crash the app. Kotlin exceptions never cross into Swift unless the function is marked `@Throws`.
- **Safety nets:**
  - a remote-config kill switch for each risky feature, shared by both apps;
  - a minimum-version check per platform (In-App Updates on Android, an App Store link on iOS).

## Scalability (client side)
- **Modularise** along the [module layout](architecture.md#module-layout), so features and teams scale independently.
- **Keep builds fast:**
  - build cache, configuration cache, no needless `api` dependencies;
  - Kotlin/Native: link only the simulator architecture locally; cache `~/.konan` in CI; run iOS jobs on macOS runners only where they're needed.
- **Protect the backend.**
  - Delta sync with server tokens.
  - Coalesce identical requests.
  - Paginate everywhere.
  - Add jitter to scheduled syncs, so devices don't all hit the server at once.
- **Feature flags** separate deploying from releasing, and let you shed load in an incident.

## Observability
- **Crash reporting on both platforms.**
  - Android: crashes and ANRs, with CI uploading the R8 mapping file for every release.
  - iOS: crashes and hangs, with CI uploading the dSYMs, including the Kotlin framework's.
  - A Kotlin exception on iOS otherwise shows up as an anonymous native crash. Use the crash reporter's Kotlin integration (e.g. CrashKiOS for Crashlytics, or the Sentry KMP SDK) so the Kotlin stack trace is reported.
- **Store metrics.** Android vitals in Play Console (crash rate, ANR rate, startup, slow and frozen frames, excessive wake-ups). On iOS, the Xcode Organizer and MetricKit (crashes, hangs, launch time, memory, disk writes). Break them down by version and device.
- **Performance monitoring:** custom traces for key journeys (e.g. "open note"), plus network latency and error rates, on both platforms.
- **Analytics.**
  - Events come from the tracking plan, with `snake_case` names and documented parameters, sent through the common `AnalyticsTracker`, so both apps send the same events.
  - Analytics is gated by consent (and ATT where it applies) and carries no PII.
- **Logs.** Kermit, with debug output in debug builds. In release, only breadcrumbs without PII go to the crash reporter.
- **Correlation IDs.** A Ktor plugin or `defaultRequest` header adds a request ID, so a user's call can be traced in the backend.
- **Release dashboard per platform:** crash-free users, ANR or hang rate, and adoption for each version. It drives the staged-rollout and phased-release decisions.
